# FUXA projects

`build_project.py` builds every FUXA project of the range from the tag lists
and the alarm list of plantgen. The range is the training network of the
brewery. A tag is a named value of a controller. The plant has three variants:
ci, full, and lite.

This file describes the ci project first. Then it describes
[the full and lite projects](#the-full-and-lite-projects), the
[process graphics](#the-process-graphics) that every project has, and the
[brewhouse batch engine](#the-brewhouse-batch-engine) on scada-fuxa.

| File | What it is |
|---|---|
| `build_project.py` | Builds a project: devices, tags, alarms, the generated points tables, the Batch view, the layout |
| `hmi_base.py` | What the builder and the graphics share: ids, the colors of the brand, the plantgen records, the plain view builder |
| `hmi_kit.py` | The drawing kit of the process graphics: vessels, scales, flags, pumps, pipes, trends |
| `hmi_views.py` | The screens, laid out with the kit |
| `batch_engine.js` | The brewhouse batch engine (a FUXA server script) |

## The ci project

`scada-fuxa-project.json` is the project that `cm-fuxa-provision` sends with a
POST request to the `/api/project` path of FUXA on scada-fuxa ([DESIGN.md
12.2](../docs/DESIGN.md#122-fuxa-two-instances)). Do not edit this file by
hand. The builder generates it.

```shell
python3 -I build_project.py          # rewrite scada-fuxa-project.json
python3 -I build_project.py --check  # fail if it is stale
```

The builder reads `plant/generated/ci/fuxa/scada-fuxa-tags.json` and
`plant/generated/ci/alarms.json`. Thus the tag IDs, the addresses, and the
alarm texts always come from `plant.yaml`. After a change, run plantgen. Then
run `build_project.py`. Then run `../sync.py`, which copies the project into
`phenix-injects/fuxa/`.

## Contents

- Device `plc-cellar`: The device uses Modbus TCP to `10.20.10.12`, unit 1.
  FUXA polls the device every second. The device has the 61 generated tags.
  The addresses are 1-based, as FUXA expects (FUXA subtracts 1). Analog values
  use the `divisor` of FUXA (raw / 100).
- View `Cellar`: The view is the [Cellar graphic](#the-process-graphics) with
  the four fermenters. The view shows these items:
  - The side temperature and the cone temperature, with their setpoints. A
    setpoint is a target value. The setpoints are writable.
  - The glycol jackets, which cool the tanks.
  - The head pressure and the spunding valve. The spunding valve holds the
    pressure of the tank.
  - The extract, which is the dissolved sugar in the beer.
  - A flag for each of the five alarm bits.
  - Two trends.

  The builder draws the bright tanks, the transfer, and the fermentation
  profile only where the plant has them (full and lite). The bright tanks hold
  the finished beer. Pressures are absolute (psia), as the PLC stores them. A
  PLC is a programmable logic controller.
- Alarms: The project has one FUXA alarm for each PLC alarm bit (20 in ci). An
  alarm is active while its bit is 1. The on-delay is the time that a condition
  must last before the alarm. The PLC applies the on-delay, so the delay of
  FUXA is 0. The severity comes from `fuxa_severity` in `alarms.json`.
- DAQ (the storage of tag values): FUXA stores the PV tags in its built-in
  SQLite database. The PV tags are the measured values. The ci variant has no
  historian. A trend also gets the hour before the view opened from this
  database.

## The full and lite projects

`build_project.py --all` also writes `full/` and `lite/`. Each directory holds
one project for scada-fuxa and one project for bas-fuxa. The cherrymountain
app builds the same projects at pre-start. Thus these files are for review and
for the `--check`.

- Devices: A project has one device for each PLC. The northbound plugin of the
  PLC gives the type of the device. A northbound plugin is the part of a PLC
  that serves a protocol to SCADA. The types are:
  - Modbus TCP for plc-cellar, plc-utilities, and plc-power.
  - OPC UA for plc-brewhouse, with the node ids `ns=2;s=<tag>`.
  - S7 for plc-packaging, with the addresses `DB<n>.DBW<byte>` and
    `DB<n>.DBX<byte>.<bit>`.

  A project also has one BACnet client device for the building controllers.
- Scaling: FUXA applies `divisor` only in its Modbus driver. The OPC UA tags
  and the S7 tags carry the same factor as a linear `scale` (`rawHigh` = the
  factor). Every driver applies this scale on reads and inverts it on writes.
  BACnet values are engineering values already.
- Views: The [process graphics](#the-process-graphics) come first. On
  scada-fuxa, the graphics are Overview, Brewhouse, Cellar, then Packaging,
  Utilities, Power, and Cellar CO2. On bas-fuxa, the graphic is Building. The
  Batch view comes after Brewhouse. A generated table for each device comes
  after the graphics. On scada-fuxa, the tables are Brewhouse points, Cellar
  points, then Packaging points, Utilities points, Power points, and Cellar
  CO2 points. On bas-fuxa, the table is Building points.

  In a table, each row is a label and a value or a lamp. A table is at most
  three columns across (1,240 px) and thirty rows down. Thus it fits beside
  the menu on the 1440x900 screen of an HMI station. An HMI (human-machine
  interface) station is the screen of an operator. A device with more tags
  (Cellar points) continues in a second band below. The page scrolls to that
  band.

  A tag that the operator can write (`access: read-write` in the plantgen tag
  list) also has an input box in its table. The box takes a number in the
  range of the tag, or 1 and 0 for a bit.

  The graphics have a box or a button for the items that an operator changes
  most. These items are the setpoints, the commands of the line and of the CIP
  (clean-in-place) skid, and the CO2 shutoff reset. The tables have every
  writable tag. Thus an operator uses a table to set an entry permit or to
  give a phase command. An entry permit lets a person go into a vessel. Its
  tags are `CEL.ENTRY.HS0n.ENTRY` on Cellar points and `BH.ENTRY.HS0n.ENTRY`
  on Brewhouse points. A phase is one process step of a brew.
- Who writes BACnet: Only bas-fuxa writes BACnet. The BACnet tags of
  scada-fuxa are read-only (DESIGN.md 10.3). The multi-state occupancy mode on
  bas-fuxa is also read-only, because the driver of FUXA writes analog and
  binary objects only.
- Alarms: The four plant priorities map to the four levels of FUXA (critical
  maps to `highhigh`). An operator must acknowledge every level but the
  lowest. A PLC alarm bit carries its own on-delay. An alarm that FUXA
  evaluates on a BACnet value gets the rationalized on-delay as `timedelay`.
  FUXA has no deadband. A deadband is a margin that the value must cross
  before the alarm clears.

## The projects of the sites

`build_project.py --all` also writes `fleet/<code>/`. This directory holds one
project for each FUXA host of each site of the fleet. A site is the plant with
parts left out and with its own hostnames
([plantgen README](../tools/plantgen/README.md#sites)). `--check` covers these
projects, too.

```shell
python3 -I build_project.py --site fc          # the SCADA host of one site
python3 -I build_project.py --site cs --host cs-bas-fuxa
```

| Site | FUXA hosts | Screens of the SCADA host |
|---|---|---|
| `fr` | `fr-scada-fuxa`, `fr-bas-fuxa` | The screens of the whole plant |
| `ep` | `ep-scada-fuxa`, `ep-bas-fuxa` | The screens of the whole plant |
| `cs` | `cs-scada-fuxa`, `cs-bas-fuxa` | No Power screen |
| `fc` | `fc-scada-fuxa` | No Packaging screen and no Power screen. It has the Building screen |

The builder reads the plantgen output of the site,
`plant/generated/fleet/<code>/`. It knows no hostname:

- A FUXA host is a tag list in that directory. The default host is the first
  host that reads a PLC.
- A device is a PLC or the BACnet client by its type. The name of its points
  table comes from the area of its tags (`BH` gives "Brewhouse points").
- A caption or an alarm text that names a controller takes the name from
  `tags.json`. At `cs`, a caption says `cs-plc-cellar`.
- The batch engine goes to the host that reads the state tag of the brewhouse
  PLC.

The screens follow the tags of the host:

- A host that reads the brewhouse gets the Overview and one screen for each
  area that its tags cover. The Overview has one panel for each such area.
- A host that reads the building controllers gets the Building screen.
- `fc` has no building front end. Its one SCADA host reads all of the points
  of the building and writes them, so it has both sets of screens. On its
  Overview, a Building panel has the place of the Power panel.
- At `fc`, the BACnet device has a `broadcastAddress`, as the device of
  `bas-fuxa` has. The controllers are on the network of the SCADA host, and
  the site has no BBMD. plantgen sets this value (`render.py`, `fuxa_doc`).

The batch engine reads and writes tags of the brewhouse PLC and of the cellar
PLC only. Thus a site without packaging or power runs the same script. The
tests run two engine scenarios on the project of each site.

A test walks every project. It makes sure that each tag, view, chart, and
device that the project uses is in the project.

These parts are not done:

- The cherrymountain app and `sync.py` do not use the projects of the sites.
- The comments in `batch_engine.js` still say `scada-fuxa` and `plc-cellar`.
  A change there changes the bytes of the full and lite projects.
- The CO2 screen of `fc` shows a sensor at the filler, and `fc` has no
  filler. The building controller still has that point.

## The process graphics

`hmi_views.py` draws the screens that an operator works from. It uses the kit
in `hmi_kit.py`. The screens follow the high-performance HMI practice of
ISA-101.

The hierarchy:

| Level | View | What it is for |
|---|---|---|
| 1 | Overview | The whole plant at a glance. The product moves from left to right. The view shows the brewhouse vessels, the fermenters, and the bright tanks. It shows the state of the line and its OEE (overall equipment effectiveness). It shows the utilities on scales, the power one-line (the diagram of the electrical system), the CO2 of the cellar, and two trends. The view has nothing to operate. A click on a panel opens its area |
| 2 | Brewhouse | The vessels as they stand, the phase of the batch across the top, and steam along the bottom. The view also shows the knockout to the cellar. The knockout is the transfer of the wort to a fermenter. The wort is the sugary liquid before fermentation |
| 2 | Cellar | The four fermenters and the two bright tanks, the racking line and the transfer pump, the setpoints, and the stage of the profile |
| 2 | Packaging | The line from glass to cases with the PackML state of each machine, the commands of the line, and the keg line |
| 2 | Utilities | Glycol, steam, air, CO2 supply, water, wastewater neutralization, and the CIP skid with its steps |
| 2 | Power | The one-line diagram: service, switchboard, PV (here, the solar panels), battery, feeders, transfer switch, generator, demand |
| 2 | Cellar CO2 | Where the CO2 comes from, what the sensors read, and what the detection did. The view shows the supply and its shutoff valve. It shows the cellar from above, with the purge fans. A ring is around a fermenter that vents. A flag is at a relief valve that lifted. Each sensor is on a bar cut at the three tiers. The view shows each tier with the actions of its relay and whether each action occurred. It shows the sensors of the other areas, and the last hour (read only) |
| 2 | Building (bas-fuxa) | The building as a plan: the taproom and RTU-1, the cold room, and the brewhouse hood. The view also shows the plan and the tiers of the cellar as on Cellar CO2. Here they have the buttons for the purge fans and the horns |
| 3, 4 | Batch, `... points` | The controls of the batch, and every tag of a controller |

A screen is 1,240 by 820 px. This size is the 1440x900 display of an HMI
station less the menu and the header. `hmi-brewhouse` and `hmi-packaging` open
the Brewhouse and Packaging screens by name.

The rules that the kit keeps:

- Gray is normal. Equipment is gray on the process-area gray of the brand. A
  screen with nothing wrong has no alarm color on it.
- Alarm colors are only alarms. The four reserved colors of
  `brand/tokens.json` appear only in a flag. A flag is also a shape with the
  number of the priority: 1 square (critical), 2 triangle (high), 3 inverted
  triangle (medium), 4 diamond (low). A flag stands beside the value that its
  alarm watches. A flag stays hidden until its alarm is active. The text of
  the alarm is the tooltip of the flag. Every alarm of a project has a flag on
  a graphic.
- Media have their own muted colors (`MEDIA` in `hmi_kit.py`). The kit uses
  these colors for the contents of a vessel or a pipe and for nothing else.
- Running is filled and stopped is hollow, in one "live" blue. A fan that runs
  also turns. A pipe with flow in it shows the flow in motion.
- A value comes with its range. A measurement with limits is a scale. The
  scale has the normal band and each alarm limit of `alarms.json` as a mark.
  It has a pointer at the value and a hollow marker at the setpoint. A quantity (a
  level, a charge, the opening of a valve) is a fill. The level of a vessel
  fills the shape of the vessel.

  A CO2 reading is a bar cut into equal parts at the three tiers (5,000,
  15,000, 30,000 ppm). Each part fills as the reading goes through it. On one
  straight scale to 30,000 ppm, the first tier is a sixth of the bar, and
  a normal room is a sliver.
- A safety action appears with its effect. Each CO2 tier is a lamp. Under it
  is a lamp (or the fan itself) for each action of its relay. The screen reads
  each effect from the controller that does the action. A lit tier over an
  effect that is not lit shows a failed or defeated interlock. An interlock is
  a safety function that forces an action.
- A control is only on a writable tag. `Canvas.entry` and `Canvas.button`
  stop the build for a tag that is not `read-write` in the plant model.
- A wrong tag name stops the build. The kit binds every element by tag name.
  Only the Cellar asks whether the plant has the bright tanks.

The table shows how the kit writes the elements for FUXA 1.3.6. All of them
ran in a real server against a stand-in plant
([docs/examples/capture](../docs/examples/capture/README.md)).

| Element | FUXA item | Notes |
|---|---|---|
| Number | `svg-ext-value` | FUXA takes 0 fraction digits as "not set" and shows the rounding of the tag. Thus the kit asks for 1 digit on a scaled tag |
| Lamp | `svg-ext-gauge_semaphore` | One circle whose fill follows `ranges` |
| Valve, breaker, wire, jacket, the contents of a fermenter, the ring around a vessel that vents | `svg-ext-shapes-*` with `ranges` | Any SVG element whose id starts with `svg_`. A range sets its fill, or its stroke for a wire or a ring |
| Fill, pointer, setpoint marker, a part of a tier bar | `svg-ext-shapes-*` with a `moveByTags` action | FUXA moves the element between two positions as the tag goes from one value to another. FUXA holds the element at the ends. Thus a tier bar can be three fills side by side, one for each span. A fill moves behind a `<clipPath>` of the outline of the vessel. The kit does not use `svg-ext-gauge_progress`, because that item draws an empty bar for a value above its range |
| Alarm flag, the word of a state | `svg-ext-shapes-*`, `hide: true`, with `show` and `hide` actions | A PLC alarm bit shows its flag at 1. An alarm that FUXA evaluates shows its flag past the limit. A word is one hidden text for each state |
| Fan blades | `svg-ext-shapes-g` with `clockwise` and `stop` | An unseen circle centers the box of the group on the hub. FUXA turns the group about the hub |
| Pipe with flow | `svg-ext-pipe` with `clockwise` and `hidecontent` | FUXA scrolls the dashes at a fixed speed, with a 20 ms timer for each pipe. Thus only the pipes with a pump, a valve, or a flow meter behind them move |
| Input box, button | `svg-ext-html_input`, `svg-ext-html_button` | As in the points tables. An input box also takes 0 fraction digits as "not set". Then it shows up to five decimals, and a narrow box cuts them off. Thus the kit asks for 1 digit on a scaled tag |
| Trend | `svg-ext-html_chart` (`realtime1`, 60 minutes) and an entry of the `charts` of the project | It loads the values that FUXA stored, and then it follows live values. Thus every trended tag has `daq.enabled`. The kit draws the legend. The legend of FUXA is off (`legendMode: follow` keeps the tooltip) |
| Dial | `svg-ext-html_bag` (donut) | Shift OEE only |
| Link | `svg-ext-shapes-rect` with an `onpage` click event | A transparent rectangle over a panel |

To see a change, build the projects. Then run the FUXA of the capture scripts
(`docs/examples/capture/fuxa_run.sh up scada <snapshot>`). Then open a view.

## The brewhouse batch engine

The scada-fuxa project of `full` and `lite` carries one server script,
`cmBatchEngine`, from `batch_engine.js`. It also has a Batch view after
Brewhouse ([DESIGN.md 12.2](../docs/DESIGN.md#122-fuxa-two-instances)). The ci
project does not have them, because ci has no brewhouse. The bas-fuxa project
does not have them.

The script runs every second. It sequences the ten phases of plc-brewhouse,
one brew after another. For each phase, the script does these steps in this
order:

- It sets the setpoints and the parameter of the phase.
- It commands Start.
- It waits for Complete.
- It commands Reset.
- It goes on to the next phase.

The builder reads the numbers of the recipe from
`../recipes/fire-of-the-phenix.json` and embeds them in the script. These
numbers are the grain bill, the mash steps, the boil and whirlpool minutes,
and the temperatures. Thus, to change the brew, change the recipe and run
`build_project.py`.

All batch state is in tags of the `FUXA Server` device of FUXA (`BATCH.*`).
FUXA restores these tags after a restart. Thus the batch continues from the
same point after a restart of FUXA. The Batch view shows those tags.

The operator uses the buttons on the Batch view. The buttons write
`BATCH.CMD`. The engine takes the command and clears it.

- Start adds one brew to the queue. The brew starts when three conditions are
  true. The brewhouse PLC is Idle. Neither brewhouse vessel is in
  confined-space entry (a person is in the vessel). A fermenter is empty and
  lined up (see Fermenters below). If a condition is not true, the Status line
  gives the cause, and the *Refused* alarm comes on after 10 s. The brew stays
  in the queue and starts when the cause clears.
- The engine takes Hold at the next safe point. Between phases, the engine
  holds at once. During a phase, the engine commands Hold of the PLC phase
  that runs. Then every phase output is off, and a timed step keeps the time
  that it served. Restart continues from Held. The engine refuses Restart
  while a vessel is in entry.
- Abort aborts the PLC phase, resets it, empties the queue, and ends the batch
  as *Aborted*. Reset acknowledges a Complete or Aborted batch, clears the
  queue and the alarms of the engine, and resets the PLC.

Unattended: The `start-batch` plantevent (SCORCH `baseline-brew-day`) reaches
the brewhouse federate. A federate is one simulator of the plant. The
federate counts a request at the panel (`BH.BATCH.XI02.REQUESTS`). The engine
reads this count through rio-brewhouse and plc-brewhouse over OPC UA.

The engine queues every new count. It writes the count that it took to
`BH.BATCH.XC02.ACCEPTED`, and the PLC copies that count back to
`BH.BATCH.XI03.ACCEPTED` of the panel. The engine starts the brew when the
brewhouse is ready. Thus a request that comes while FUXA is down waits at the
panel, and the engine takes it when FUXA is back. Without a PLC, the federate
runs its own autopilot instead (`sim/README.md`).

Fermenters: A fermenter is free when plc-cellar reports it empty (extract
meter at 0) and lined up (not in entry, CIP permitted). A brew does not start
without a free fermenter. Knockout then reserves the fermenter. If the batch
lost the fermenter after the start, the batch waits in KNOCKOUT, and the wort
stays in the kettle. After 10 min, the *Nofv* alarm comes on. The two brews of
a brew day go into the same fermenter, and the view then shows that fermenter
as full.

The reservation is the check and the display of the engine. The wort goes
where the cellar federate sends it. The federate sends it to the fermenter
that it already fills, or else to the first empty fermenter. That fermenter is
the reserved fermenter, unless a fermenter with a lower number is empty but in
entry.

Faults: When a phase does not complete in its timeout, the engine holds the
PLC phase, raises the *Timeout* alarm, and holds the batch. The engine does
the same, but with the *PLC* alarm, in these three cases:

- A PLC does not answer a command in 30 s.
- A PLC aborts the phase or loses the phase.
- The PLC link is down for 60 s.

A script that fails three runs in a row raises the *Engine* alarm. Every hold
names its cause on the Status line. Restart or Abort clears the hold.

`tests/` runs the generated script under Node (18 or newer). The script runs
against a stub (a stand-in) of the script API of FUXA. It also runs
against a simulator of plc-brewhouse and of the status of the cellar:

```shell
python3 -m pytest fuxa/tests         # from cherrymountain-brewery/
```

The test files are:

- `test_batch_engine.py` runs 25 scenarios. The scenarios cover these cases:
  - An unattended brew.
  - A double brew day.
  - Hold and Restart.
  - Abort.
  - A phase that never completes.
  - No fermenter at the start or at knockout.
  - Refused starts.
  - A lost link.
  - A restart of a PLC or of FUXA.
  - A request while FUXA is down.
  - A script that fails.
- `test_batch_project.py` tests what the builder writes.
- `test_brand.py` compares the frame and the process views with
  `brand/tokens.json`.
- `test_plc_port.py` compares the handshake of the simulator with the compiled
  program of plc-brewhouse, scan by scan. This test needs strucpp and g++, as
  `sim/tests/st_engine.py` does. Without them, the test skips.
- `sim/tests/test_brewhouse_control_path.py` runs the script against the
  compiled PLC and the federates.

## The brand on FUXA's screens

Both FUXA hosts have the frame of the brewery
([brand/README.md](../brand/README.md)). Ink, paper, ember, and coal are
colors of the brand. The mark is the logo of the brewery. The frame has these
parts:

- The header is ink with paper text. It has the name of the brewery and a 3 px
  ember stripe under it.
- The menu is coal with paper text. It has the full mark (48 px) at its top.
- The tab has the icon of the brewery and the title "CherryMountain Brewery
  SCADA" (or "... BAS").
- The sign-in dialog is a coal card with the mark above its title, ink fields,
  and an ember OK button.

The process views keep their gray background and their own colors. The alarm
levels keep the reserved colors. The table shows where each piece comes from:

| Piece | Mechanism | Source |

The menu template `sidenav.component.html` shows `logo` in place of the title of FUXA |
| The name in the header | A header item of type `label` with the name in `property.text`. FUXA reads `header.title`, but its home template never shows it | `home.component.html` (`header-items-button`), `home.component.ts` `loadHeaderItems` |
| The ember stripe, the signed-in icon, the row of the mark, the sign-in dialog | `layout.customStyles`, a CSS string that FUXA adds to every page. `frame_css()` writes it with the token colors. Every rule starts at `.header`, `.sidenav-menu`, `.mat-mdc-dialog-container:has(app-login)`, or `app-login`. Thus no view takes a rule | `app.component.ts` `applyCustomCss`. | The tab icon | `brand/favicon.ico`, injected over `/opt/fuxa/client/dist/favicon.ico` | `client/dist/index.html` links `favicon.ico` |

- The frame colors are the tokens.
- The CSS names only brand colors, and no alarm color.
- Every rule starts in the frame.
- No view paints a brand color.
- The alarm levels keep their reserved colors.
- The buttons of the Batch view keep their own readable style.

A run in a real FUXA 1.3.6 showed the brand rendered. The run had this setup:

- The pinned commit, with the `node-opcua` and `modbus-serial` drivers and with

## Checked against FUXA source

The items below come from a comparison with `frangoteam/FUXA` at `b2972583`
(server 1.3.6). The `cm-fuxa` image pins this commit.

- Project sections and how `setProject` stores them (`server/runtime/project`).
- Modbus tag fields, memory areas, and the 1-based `address`
  (`server/runtime/devices/modbus`). FUXA reads the Modbus TCP port from an

  `async function name () { try {...} catch (fuxaError) {...} }`
  (`server/runtime/scripts/msm.js`). Thus FUXA logs an error, and the error
